# 9. 3D

Status: design, 2026-10-25. Nothing is built. Tom's direction
(2026-10-25): one tree for 2D and 3D; CSS 3D transforms on elements
first, enough for touché's layer view (animating into a 3D view of the
layers to navigate, select, move and remove); the render tree designed
now so a node can host a scene with its own camera and depth; later a
threlte-like `<scene>`, `<mesh>`, `<camera>` with typed props, a small
prefixed list of CSS extensions for presentation, flat ECS-like scene
data, and bulk animation outside per-object signals.

## The model

### Stage 1: CSS 3D transforms on elements

`transform` with the 3D functions (`translate3d`, `rotateX/Y/Z`,
`rotate3d`, `scale3d`, `matrix3d`, `perspective()`), `transform-origin`
with a z component, `perspective` and `perspective-origin` on the
parent, `transform-style: preserve-3d | flat`, `backface-visibility`.
Semantics are CSS Transforms 2: each element has an accumulated 3D
matrix; a `flat` parent (the default) projects its children's 3D into
its plane; a `preserve-3d` parent keeps them in one 3D space and the
grouping properties (`opacity < 1`, `overflow` other than `visible`,
`filter`, `clip-path`, `mask`, `mix-blend-mode`, `isolation: isolate`)
force flattening, as the specification lists. Transforms do not affect
layout; they affect paint and hit testing, which maps the pointer
through the inverse matrix (a non-invertible matrix hits nothing).

Paint: an element with a 3D transform becomes a **layer** (the same
mechanism area 6's opacity groups use): its subtree is painted to a
texture at the resolution its screen footprint needs, and the layer is
composited as a textured quad transformed by its matrix, with
perspective division in the vertex shader. Within a `preserve-3d`
context, layers are sorted back to front by depth; the specification
describes a Newell-style sort that splits intersecting planes, and
vapors does not split, as Chromium does not either. `perspective` on
an element makes it a stacking context and a containing block, as the
specification says. A back face is hidden when the accumulated
matrix's `m33` is negative. Text inside a transformed layer is rasterised at the layer's
scale, so it stays sharp when the layer is scaled up, and is
resampled by the transform; this matches Chromium's behaviour of
re-rastering on scale changes after the animation settles.

This is enough for the layer view: each layer card is a `preserve-3d`
child with `rotateY` and `translate3d`, transitioned by area 6, under a
`perspective` parent; a tap on a card is a pointer event mapped through
its inverse matrix, so the existing dispatch serves.

### Stage 2: the render tree hosts scenes

The element tree gains a node kind, `scene`, whose children are scene
objects rather than elements. In the display list a `scene` is one item
with its own camera, depth buffer and viewport (its border box). The
painter renders it in paint order like an image, so a scene sits in a
card, scrolls with a list and is clipped by its container. Elements
carry 4x4 transforms from stage 1, so the tree already has the
representation.

Scene objects: `<mesh>`, `<camera>`, `<light>`, `<group>`, `<instances>`,
`<texture>`, `<gltf>`. Each is a tag in the template with typed props:

```html
<scene>
  <camera kind="perspective" fov={45} position={[0, 0, 6]} look_at={[0,0,0]} />
  <light kind="directional" intensity={2.0} direction={[1,-1,-1]} />
  {for layer in layers key=layer.id}
    <mesh geometry={plane(1.5, 1.0)} material={Material::unlit(layer.texture)}
          position={[0, 0, -layer.index as f32 * 0.4]} class={selected(layer)}
          onclick={select(layer)} />
  {/for}
</scene>
```

Props are Rust types (`Vec3`, `Quat`, `Geometry`, `Material`,
`Texture`), checked by the compiler as any prop. Physical data (geometry,
material model, light intensity, camera) is props only. A short list of
**presentational properties** is CSS, prefixed, so themes and tokens
apply to 3D: `--vapors-color` (a token colour tint), `opacity`,
`visibility`, `--vapors-emissive` (a highlight for selection and
hover), `transition-*` for those, and state selectors (`.selected`,
`:hover` through picking). Unknown properties on a scene object are
refused, as everywhere. `transform` on a scene object is refused in
favour of `position`, `rotation` and `scale` props, so there is one
answer to where an object is.

**Picking** is hit testing: a ray from the camera through the pointer,
intersected with bounding volumes then triangles, in the same hit test
pass as elements; the hit scene object is the target of the ordinary
pointer events and `:hover`. A scene with no listeners is skipped.

**Scene data is flat.** The scene's objects live in arrays indexed by
object id (positions, rotations, scales, material ids, geometry ids,
flags), with a world-matrix array computed per frame from the parent
chain, the same shape Bevy's `Transform`/`GlobalTransform` propagation
has. Props from the template write into these arrays through the usual
one-effect-per-hole; nothing per object is retained beyond its row. A
row's field has one writer: a field bound by a prop in the template is
written only by that prop's effect, and a bulk task may write only
fields with no prop binding (a task writing a bound field is refused in
debug, naming the object and field). So an animated fan-out binds
nothing to `position` and lets the task own it, or binds `position` and
animates by writing the signal. The renderer uploads changed rows to GPU buffers and draws instanced,
grouped by (geometry, material), so a thousand layer thumbnails are a
handful of draws. On the web, fewer and larger draws matter because
every WebGPU call crosses the JS boundary (Tom's note).

**Bulk animation is a frame task.** Per-object signals are for state
that is per object by nature (selected, a position the user dragged).
An animation that moves every object (the fan-out into the 3D view, a
camera path) is a task registered on the scene, called in the animation
tick (area 2 phase 3) with `frame.now`, writing the arrays directly, or
a compute shader writing the instance buffer. This is threlte's
`useTask` shape and R3F's `useFrame`, with the same stage ordering
(before or after another task by name).

**Textures are the engine's.** A `<texture>` prop can be a wgpu
texture the engine owns (a layer's render result), because there is one
device (ARCHITECTURE.md). The scene draws it directly as a material;
nothing is copied.

### Stage 3: glTF and extras

A `<gltf src>` loads a model through area 7's storage and area 1's
`await`; materials are PBR via a Rust glTF crate's data model; `extras`
such as orbit controls are components written in `.wisp` over the
scene's camera props. None of this is scheduled for touché.

## Taken from where

- **CSS Transforms 2**: stage 1, taken as the specification, including
  flattening and the grouping property list, so Chromium is the oracle.
- **threlte**: the `<T.X>` component model where a tag is a scene
  object and attributes are its typed properties; the task scheduler
  with named stages; interactivity through the same event dispatch;
  state through the framework's own signals. Differs: vapors' objects
  are a fixed, typed vocabulary, not a reflection over three.js; CSS
  applies to a small presentational subset.
- **React Three Fiber**: `useFrame` priority and demand-driven
  rendering (`invalidate`), which is vapors' redraw on demand.
- **Bevy**: flat component arrays with transform propagation; instanced
  draws keyed by mesh and material; picking as pointer events on
  entities with bubbling through observers. Differs: no ECS systems
  scheduler; the frame has fixed phases.
- **Xilem/Vello**: not taken for 3D; Vello is 2D vector.
- **CSS 3D in Chromium**: the compositor's layer promotion for
  transformed subtrees is the model for stage 1's layers.

## Deliberately left out

- A general scene graph with arbitrary nesting depth and per-node
  signals: `<group>` nests, but world matrices are computed in the flat
  arrays, not through per-node memos.
- Physics, skinning, animation clips, post-processing stacks, shadows
  beyond one directional shadow map: none has a touché need.
- Splitting intersecting `preserve-3d` planes.
- `transform` on scene objects; `perspective` as a scene property.
- WebGL fallback: WebGPU only, as everywhere.

## Oracles

| Part | Oracle |
|---|---|
| 3D transforms on elements | Chromium: geometry through `getBoundingClientRect` (the projected box) and paint through the three pixel rules at 1x and 2x for rotated, perspective and `preserve-3d` fixtures; WPT `css/css-transforms/` reftests for `transform-style`, `backface-visibility` and `perspective` run as pixel comparisons; `elementFromPoint` for hit testing through the inverse |
| Flattening rules | A fixture per grouping property, each compared with Chromium |
| Transform interpolation | WPT `css/css-transforms/animation/` cases (matrix decomposition) with a stepped clock |
| Scenes | Reference renders: a fixed scene rendered on lavapipe, compared pixelwise to a committed image (there is no browser oracle for a wgpu scene); the determinism check renders twice |
| Picking | A test that clicks on known object positions and asserts the target; a transform chain checked against a CPU reference |
| Instancing | Draw count per frame pinned; a thousand objects in a stated budget on this machine |
| Bulk animation | The arrays after N ticks equal a CPU reference; no signal written during the tick, asserted |
