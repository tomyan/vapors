# Timing baseline, 2026-11-10

IU1 PR 4 (docs/plans/iu1.md). Release timings of the rows and racer
workloads in `crates/perf` (vapors-perf). Timing is reported here, never
asserted in CI.

## Setup

- Revision: 2b20ec1 (branch `perf/iu1-4-timing`, PR #180) for runs 1
  and 2; the commit that adds this file changes only docs. Run 3 (draw's
  split) is at ba80b9d, which adds the `draw step` spans.
- Profile: release (`cargo build --release -p vapors-perf`).
- Hardware: Intel UHD Graphics 630 (CML GT2), Mesa 25.0.7 (ANV),
  backend Vulkan, timestamp queries available. Headless, no display.
- Scale 1. Viewport 640 x 400 for the rows workloads, 1100 x 720 for
  the racer.
- Target: offscreen. The sampler makes one texture per workload
  (`clear` in `sampler.rs`) and passes it to `App::frame` in `Frame`;
  there is no surface, so no `get_current_texture` and no present
  (acquire lives in vapors-platform's `surface_texture.rs`, which the
  harness does not use). `draw` therefore never waits for the display
  or vsync; it is the painter's own work, its encoding, its queue
  writes and its submits. A windowed
  app with a Fifo surface adds the acquire wait on top, which this
  baseline does not measure.
- Sampling: 20 warmup frames, then 200 timed frames per workload. Each
  frame is one `App::frame`. Between frames, untimed, the sampler waits
  for the GPU (10 s deadline), so a frame never includes earlier frames'
  queued work. Each table gives median, p90 and max (nearest rank).
- Load: the 1-minute load average was 1.29 at the start of run 1 and
  1.00 at its end; 1.00 at the start and end of run 2. Other agent work
  was paused for the measurement.
- Workloads: 100, 1000 and 3000 rows (`crates/elements/tests/support/
  rows_page.rs`), each with nothing changed (Idle), one row's value text
  changed (Text), or one row's `marked` class toggled (Class) before
  each frame; the racer paused (HUD values unchanged) and racing.

## Instruction counts

`--instructions` reports, per workload, the median user-space
instructions the calling thread retired per frame, for the frame and
each phase the table above times (CPU side only: GPU work on other
threads, such as lavapipe's workers, is not counted). It reads Linux perf
events from inside the process (`perf-event2`), so the count follows the
code run and, for the workload measured below, barely moves with machine load. Use it for a performance PR
on a busy machine; keep wall-clock runs, on a quiet machine, for
milestones.

```
cargo build --release -p vapors-perf
./target/release/vapors-perf 60 10 --instructions --only "3000 rows, Class"
```

`--instructions` first checks its counter: it runs a loop the optimiser
cannot fold and refuses unless the count rises by at least the loop's
instructions. It refuses a reading whose counter was not running for the
whole time it was enabled (another perf user, or the NMI watchdog, took
the counter: `sysctl kernel.nmi_watchdog=0`), and a workload with a timed
phase that has no count.

`--only <substring>` (given once) runs the workloads whose name contains the
substring, in either mode; one that matches nothing is refused with the
names listed. The counts include the harness's span bookkeeping, which is
the same for a base and a branch. Compare a branch with its base, built
the same way; counts differ between compilers and CPU models.

Where perf events cannot be opened, `--instructions` fails naming
`kernel.perf_event_paranoid`; it never reports time instead. User-space
counts need the value at 2 or lower (Debian's default is 3), and the
setting is lost on reboot: `sudo sysctl kernel.perf_event_paranoid=1`.

on lavapipe: three runs of

## Findings

1. Draw is 87% to 95% of the frame in every workload. Draw time divided
   by draw calls is 71 to 77 µs in every workload (22.5 ms / 317 calls
   at 100 rows, 215 ms / 3017 at 1000, 654 ms / 9017 at 3000, 2.6 ms /
   33 in the racer). Each pipeline's draw in vapors-renderer
   (`instanced.rs`, `image.rs`) and vapors-text (`draw.rs`) makes its
   own bind group, encoder and render pass, writes its buffers and calls
   `queue.submit`. Run 3 times those steps (below): per draw call at 100
   and 1000 rows idle, `Queue::submit` takes about 35 µs, the bind
   group, encoder and render pass about 25 µs, and the buffer writes
   about 10 µs; the rest of draw, the painter's own work, about 5 µs.
   Submit is 46% to 47% of draw, encoding 32% to 33%, writes 13%.
2. The GPU span bounds GPU time from above only. The span is two
   timestamps, each in its own submit, before and after the frame. In
   the rows workloads it equals the CPU frame time to within 0.03 ms,
   because the GPU waits between the painter's submits and the span
   includes those waits; it says nothing about the GPU cost of the
   draws themselves. In the racing racer it is 8.2 to 8.6 ms against a
   3.0 ms CPU frame: the closing timestamp runs after the track's
   rendering finishes on the GPU. Measuring GPU time itself needs
   timestamps around each render pass (`timestamp_writes` in
   vapors-renderer's pipelines) or one encoder per frame; both are
   renderer changes, not made here.
3. Update against draw, the shares of the CPU frame (median, both runs):
   rows at 100: update 5% to 7%, draw 93% to 95%; at 1000: update 8% to
   9%, draw 91% to 92%; at 3000: update 9%, draw 90% to 91%; racer
   paused: update 7% to 8%, draw 91% to 93%; racing: update 12%, draw
   87% to 88%. On this machine draw takes 7 to 18 times as long as
   update (7 in the racing racer, 18 at 100 rows idle), so the painter's
   per-draw-call submits are a larger cost than what IU3 (retained
   layout) targets. Update alone is still
   linear in rows: 1.3 ms at 100, 19 to 20 ms at 1000, 66 to 68 ms at
   3000, with layout the largest of its three phases.
4. Text and Class edits cost about the same as Idle: the whole tree is
   walked and every box drawn on every frame (docs/plans/iu1.md PR 2 and
   PR 3), so one row's change is a small part of the frame.
5. The paused racer lays out 20 boxes every frame (Counts: laid out 20)
   although its HUD values do not change. Not investigated here.

### Update rose, and #181 does not change update

Update is longer after than before in every workload (100 rows idle
1.27 → 2.16 ms, 1000 rows 19.3 → 20.9 ms, racer racing 0.37 →
1.05 ms), and style, layout and paint each rose by about the same
factor. Runs on 2026-11-11, back to back, update medians in µs. The
first two columns' runs were `vapors-perf 60 10`, the 2b20ec1 one
starting at load 6.80 just after the builds (the 03c4514 one ran
right after it); the others `30 5`, at load 1.59 and 0.65. The 03c4514
numbers match the lead's quiet run of 9a885b8 above (racer paused 518
against 531 µs).

| workload | 2b20ec1 (baseline) | 03c4514 (#181) | b8de785 (main) | 03c4514, GPU wait spun |
|---|---|---|---|---|
| 100 rows, Idle | 1325 | 1559 | 1315 | 1407 |
| 1000 rows, Idle | 19087 | 20888 | 18994 | 19811 |
| 3000 rows, Idle | 62509 | 74840 | 66801 | 70185 |
| racer, paused | 187 | 518 | 188 | 174 |
| racer, racing | 350 | 1057 | 350 | 267 |

The baseline revision and main reproduce the baseline's update today,
so the rise is not machine state, and at 100 and 1000 rows and in the
racer it is not in main; it comes with the #181 branch. The harness waits for the GPU after each frame
(`gpu_time::wait`, a blocking `Device::poll`) and the next frame begins
with update. Before #181 the GPU kept up with the per-draw submits and
the wait was short; now the GPU starts at the frame's one submit, so
the thread blocks for most of the GPU's work. The CPU runs
`intel_pstate` in `powersave`, and the column "GPU wait spun" replaces
the blocking wait with a loop of non-blocking polls (a local change,
not committed): update falls back to the baseline or below for the
racer and to within 4% to 6% at 100 and 1000 rows. The finding: most of
the rise is the core clocking down while the harness thread sleeps in
the GPU wait, and update then runs at a lower clock. At 3000 rows the
spinning wait leaves update 5% over main's, and main's is itself 7%
over the baseline's; neither difference is explained here.

An app on a surface waits in `get_current_texture` rather than in a
poll, so this harness effect does not carry over to it as measured;
part 2's active CPU time and acquire wait per frame are the numbers to
read for that.
