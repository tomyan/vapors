# Mount and first frame, 2026-11-12

Analysis PR 1 (finish-line properties 7 and 8). The `Mount` workload in
`crates/perf` (vapors-perf): a compiled `{for}` of row components
(`crates/perf/ui/mount_rows.wisp`, `mount_row.wisp`) mounted under the
body of a new document, then the app's first frame. Each row is a
`div.row` with a `class:marked` directive, two `span`s with text and a
`button`, so 4 elements and 3 text nodes per row, with the rows' own
`<style>`. Run with `vapors-perf 9 --mount`.

## Setup

- Revision: c282ca0 plus this change. Release build.
- Hardware: Intel UHD Graphics 630 (Mesa 25.0.7, ANV), headless,
  viewport 640 x 400, scale 1. The frame is drawn into one offscreen
  texture as in the other workloads.
- Sizes: 1000, 3000 and 10,000 rows (`scaling::SIZES`).
- Sampling: 1 untimed page, then 9 kept pages per size. Every kept
  page is a new document, new component and new `ElementsApp`, so each
  frame is that app's first. The sampler times `App::frame`
  (`update`, `draw` and the app's other phases); `MountRows::mount` is
  timed and counted by the workload before it. Instructions are the
  calling thread's user-space count (`--instructions`' counter, opened
  twice: once for the frame's phases, once for the mount), median of the
  kept pages.
- GPU time is not kept: the app reads a frame's GPU time at its next
  frame, and a first frame has no next frame (`Workload::times_gpu`).
- Memory is read from `/proc/self/status` (`VmRSS`, `VmHWM`). The
  program refuses on another platform, naming it. One process runs each
  size (`--mount-memory <rows>`, started by `--mount`): a first frame
  allocates far more than the mount keeps, and the allocator reuses
  that for the next page, so sizes run in one process understated the
  later ones (a 1000-row run left the process at 758 MB before the
  3000-row mount in a first attempt).
- Load: 1-minute load average 36.6 at the start. Counts do not move
  with load; the times below do, and are higher than an idle machine's.
  Two runs of this workload (5 and 9 kept pages) gave `style` at
  10,000 rows of 7,563,568,086 and 7,557,755,682 instructions, 0.08%
  apart.

## Resident set, first mount and first frame

| rows | before KiB | after mount KiB | after first frame KiB | peak KiB | mount growth KiB | bytes per row, mount and frame |
|---|---|---|---|---|---|---|
| 1000 | 66,152 | 73,524 | 170,736 | 170,736 | 7,372 | 107,094 |
| 3000 | 66,396 | 87,380 | 359,272 | 359,272 | 20,984 | 99,968 |
| 10000 | 67,212 | 135,884 | 1,040,700 | 1,040,700 | 68,672 | 99,685 |

The mount keeps about 7,000 bytes per row (68,672 KiB over 10,000
rows) and the first frame about 93,000 more, so 1 GB resident at
10,000 rows. The peak equals the after-frame reading: the frame is the
largest allocation, and nothing after it is higher.

## What it decides

Style dominates, and it grows per row at a steady cost: 755,000
instructions per extra row for 4 restyled elements, about 189,000 per
element, in both the 1000 to 3000 and the 3000 to 10,000 steps. Layout
is next at 245,000 per row (13 laid-out boxes: about 19,000 each). The
mount itself is 3% of the time to first draw and node building
(`mount` plus `paint`'s boxes) is not the dominant cost here.

So analysis PR 2's target is style: sharing computed styles across
elements with the same key, as the spec has it. Layout is the second
target and PR 2 does not touch it. The per-row memory (about 100 KB per
row, 93% of it in the first frame, not the mount) is a second finding
for property 8 that the spec's "RSS before and after mount" would have
missed: the mount's own 7 KB per row is small beside it.
