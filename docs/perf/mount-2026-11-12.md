# Mount and first frame, 2026-11-12

Analysis PR 1 (finish-line properties 7 and 8). The `Mount` workload in
`crates/perf` (vapors-perf): a compiled `{for}` of row components
(`crates/perf/ui/mount_rows.wisp`, `mount_row.wisp`) mounted under the
body of a new document, then the app's first frame. `--mount` reports
and does not judge: unlike `--scaling` it asserts no growth bound, so
the linearity stated below was read off these tables, and a regression
in it would show only in a later run of this one. Each row is a
`div.row` with a `class:marked` directive, two `span`s with text and a
`button`, so 4 elements and 3 text nodes per row, with the rows' own
`<style>`.

Run: `cargo run --release -p vapors-perf -- 9 --mount`. It needs
Linux perf events (`kernel.perf_event_paranoid` 2 or lower; the counter
refuses and names the sysctl otherwise, and `kernel.nmi_watchdog=0` if
the counter was multiplexed). The 9 is also the most kept per size
(`mount_run::MAX_RUNS`); the run prints what the command line gave and
what was used.

## Setup

- Revision: measured at adc1973 (branch `perf/mount-workload`, PR #232,
  on c282ca0); later commits on the branch change only this file. Check
  out that sha, or the merge sha once it is merged and recorded here.
  Release build.
- Hardware: Intel UHD Graphics 630 (Mesa 25.0.7, ANV), headless,
  viewport 640 x 400, scale 1. The frame is drawn into one offscreen
  texture as in the other workloads.
- Sizes: 1000, 3000 and 10,000 rows (`scaling::SIZES`).
- Sampling: 1 untimed page, then 9 kept pages per size. Every kept
  page is a new document, new component and new `ElementsApp`, so each
  frame is that app's first. The sampler times `App::frame`
  (`update`, `draw` and the app's other phases); `MountRows::mount` is
  timed and counted by the workload before it. Instructions are the
  calling thread's user-space count (`--instructions`' counter, opened
  twice: once for the frame's phases, once for the mount), median of the
  kept pages.
- GPU time is not kept: the app reads a frame's GPU time at its next
  frame, and a first frame has no next frame (`Workload::times_gpu`).
- Memory is read from `/proc/self/status`. The program refuses on
  another platform, naming it. One process runs each size and a 0-row
  baseline (`--mount-memory <rows>`, started by `--mount`): a first frame
  allocates far more than the mount keeps, and the allocator reuses that
  for the next page, so sizes run in one process understated the later
  ones (a 1000-row run left the process at 758 MB before the 3000-row
  mount in a first attempt).
  The figures are `RssAnon`, the anonymous part of the resident set
  (heap and stacks, no file pages: code, fonts, shader caches), read
  before the mount, after it and after the first frame. They are
  high-water marks of what the glibc heap holds, not live bytes: memory
  the frame freed and glibc kept is in them. A frame that allocates and
  frees is therefore counted at its peak. The `peak` column is `VmHWM`,
  which does include file pages (about 58 MB of it at 0 rows) and is the
  figure for what the process needs, not for what pages keep.
- Load: 1-minute load average 17.8 at the start of the run below.
  Instruction counts do not move with load. Two runs of this workload
  (5 and 9 kept pages) gave `style` at 10,000 rows of 7,563,568,086 and
  7,557,755,682 instructions, and a third 7,567,356,510: within 0.13%.
  This file keeps no times: the ones first taken were at load 36, and
  the frame's times at these sizes are 0.3 to 2.4 s.

## Anonymous memory, first mount and first frame

One process and one page per size. A second run of the same sizes gave
after-first-frame readings of 13,196, 113,464, 303,196 and 989,412 KiB
against 13,196, 112,692, 301,252 and 982,584 KiB below (0.1% to 0.7%
apart).

| rows | anon before KiB | anon after mount KiB | anon after first frame KiB | peak KiB (VmHWM, all pages) | KiB per extra row, after first frame |
|---|---|---|---|---|---|
| 0 | 10,992 | 10,992 | 13,196 | 70,316 | baseline |
| 1000 | 11,080 | 18,008 | 112,692 | 171,312 | 99.4 |
| 3000 | 11,324 | 31,732 | 301,252 | 359,964 | 94.2 |
| 10000 | 12,140 | 80,364 | 982,584 | 1,041,320 | 97.3 |

The slope is between each size and the one before it, so the 0-row
page's fixed cost (the frame's pipelines, atlas and texture: 2.2 MB
anonymous at 0 rows) is not in it. The mount alone grows the heap by
6.8 KiB per row at 10,000 rows ((80,364 - 12,140) / 10,000); the first
frame's high-water adds about 90 KiB per row. Whether the frame keeps
any of that after it returns is not measured here: it needs a counting
allocator, or `malloc_trim` and a second reading.

## What it decides

Style dominates, and it grows per row at a steady cost: 755,000
instructions per extra row for 4 restyled elements, about 189,000 per
element, in both the 1000 to 3000 and the 3000 to 10,000 steps. Layout
is next at 245,000 per row (13 laid-out boxes: about 19,000 each). The
mount itself is 3% of the time to first draw and node building
(`mount` plus `paint`'s boxes) is not the dominant cost here.

So analysis PR 2's target is style: sharing computed styles across
elements with the same key, as the spec has it. Layout is the second
target and PR 2 does not touch it. The per-row memory (about 95 KiB per row of heap high-water, 93% of it
in the first frame, not the mount) is a second finding for property 8
that the spec's "RSS before and after mount" would have missed: the
mount's own 6.8 KiB per row is small beside it.
