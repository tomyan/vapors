# 3D slice 1c: the racer through a gpu-surface

Slice 1 of the 3D lane (touche `docs/decisions/2026-11-09-3d-surface-first.md`)
ends with 1c: the racer's existing renderer drawn through the surface API
behind its HUD, two independent panels, surface-local input, and the IU5
counters held per animating frame. 1a, 1b and 1b2 (#139 to #142) built the
element, the painter's surface host and `ElementsApp` mounting. The contract
is `docs/gpu-surface.md`; the counters are section f of
`docs/design/incremental-contracts.md`.

Each PR is under about 400 lines and is built by a fresh agent. Each check is
proven by breaking what it guards, watching it fail and restoring it.

| PR | Content | Status |
|---|---|---|
| 1 | Animation requests (touche decision e3, `2026-11-10-incremental-ui-contract-answers.md`): `SurfaceHandle::request_animation` and `stop_animation` replace `SurfaceRenderer::animating`; a request wakes an idle loop; requests from several surfaces coalesce into one frame; a request on an inactive surface is kept until it is painted again; the gradient example moves to the new calls | this branch |
| 2 | The racer's `Track` renderer as a `SurfaceRenderer` mounted on a `gpu-surface` behind the HUD, with no change to its scene model; the HUD's `HoldButton` reports through `on_change` / `hold_into`; the racer requests animation while racing and stops it when paused | |

## Open items from PR 1 (#147)

- **Gradient check flake.** `surface_gradient --check` failed once with
  "drew 267 frames and rendered 1 times" and has not failed since: 30 runs before the
  review, then 40 on 2026-11-10 with 12 busy loops running (37 to 81 animating
  frames each, renders = frames - 1). Cause unknown (see the exact check below). A failure now prints a per-frame trace (the
  app's `next_after_frame` reasons, each surface's flags, the asks the app
  acted on; runs of identical frames collapse to one line), so a recurrence
  in CI's log shows whether the painter stopped animating, stopped painting
  the surface, or lost the request. Start from `AppSurfaces::bring_to`.
- **`gpu_app_animation` SIGSEGV under plain `cargo test`.** About 9 of 80
  runs crash when the tests run as threads in one process (2 of 10 on
  2026-11-10 after the merge of main); `gpu_app_surfaces` crashed 2 of 80.
  nextest runs one process per test and has not crashed. Repro:
  `for i in $(seq 80); do cargo test -q -p vapors-app --test gpu_app_animation >/dev/null 2>&1 || echo fail $i; done`.
  Suspected cause: several wgpu devices per process on lavapipe; not
  investigated.
- **`ci.yml` step text.** Updated for the animating check (Tom cleared it, 2026-11-10).
- **Gradient check made exact (2026-11-10).** The check allowed
  `renders + 2 >= frames`; every one of 30 earlier runs sat at exactly
  frames - 2. The second frame without a render was a counting artefact:
  `Checked::frame` counted a frame at its start and the renderer counted
  its render later, so a count taken mid-frame included a frame whose
  render had not happened yet. Frames are now counted after the frame, and
  `Counts::now` waits for a frame in flight, so the animating second must
  have exactly one frame without a render (the script's wake frame): 40
  of 40 runs pass at frames - 1 (12 busy loops running; 68 to 81 frames). This does not explain the one failure
  ("drew 267 frames and rendered 1 times"): that would need about 266
  frames asked for without the surface rendering.
- **The original failure line.** Only "drew 267 frames and rendered 1
  times" survives (PR description); the prefix that says which count
  failed was not kept in the PR, its commits or any log on this machine.
  By the counts, "after one invalidate" (expects 2 frames) does not fit
  267 frames; "animating for" or "after stop_animation for" do. If it was
  the stop count, the app kept drawing after `stop_animation` with the
  painter's animating flag still set. A new failure's trace names the count.
