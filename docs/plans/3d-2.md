# 3D slice 2: persistent scene and camera

Slice 2 of the 3D lane (touche `docs/decisions/2026-11-09-3d-surface-first.md`;
the lane's brief is `docs/briefs/GPU_SURFACE_3D_BRIEF.md`, slice 2 under
"Implementation slices"). Acceptance, as reconciled with Tom on 2026-11-09:
show a mesh through Group/Mesh and both camera projections; prove parent
transforms, active-camera validation, invalid-input refusal and lifecycle
cleanup; compare ground and object projection so their transforms cannot
diverge unnoticed.

It also closes the two gaps IU0 found for the 3D slices
(`docs/design/incremental-contracts.md` section d): no check counts scene draw
calls, and nothing says how a scene node's signal change reaches the surface's
invalidation.

Slice 1 is done (`docs/gpu-surface.md`): the scene renderer is a
`SurfaceRenderer` on a `gpu-surface`. The racer keeps its own renderer; slice 2
does not port it.

Each PR is under about 400 lines and is built by a fresh agent. PR 2 ran over that; PRs 3 to 5 each stay under about 400 lines, splitting along file seams. Each check is
proven by breaking what it guards, watching it fail and restoring it.

## The ground and object check

A ground plane (a mesh, y = 0) carries a marker at world point P, and an object
mesh stands at P. Rendered through one camera, the marker's centre and the
object's base land on the same backing pixel, and that pixel is
`Projection::project(P)` mapped to the viewport, within one pixel, for both
projections and for a camera moved after mount. The ground and the objects go
through one view-projection matrix, so the check fails if either path takes its
own (as the racer's ground shader and solid pipeline each build theirs today).

## Decisions

Asked 2026-11-10; answered the same day.

1. **How scene nodes appear in `.wisp`** (Tom): Rust components with typed
   props, `<Scene>`, `<Group transform={..}>`, `<Mesh geometry={..}
   material={..}>`, `<Camera>`, mounted through the existing component-tag
   path. Each keeps one inert anchor element for identity and lifecycle
   (`{for}` and `{if}` anchors, the children snippet's parent); no compiler
   or document change. The docs say the anchor is `display: none` and outside
   the accessibility tree. Not chosen: lowercase elements in the document;
   a Rust API only in slice 2.
2. **The active camera** (lead): the scene root names it by handle
   (`camera={handle}`); a handle no camera holds, or held by two cameras, is
   refused, naming the fix. Not chosen: a per-camera `active` flag.
3. **Matrix maths** (lead): `glam`, pinned to an exact version, with
   `cargo xtask deny` passing; a needed `deny.toml` change stops the work
   for Tom's clear. Not chosen: our own `Vec3`, `Quat`, `Mat4`.
4. **Scene draws in `FrameCounts`** (lead): `SurfaceFrame` lets the renderer
   report its `GpuWork`, and `FrameCounts::surfaces` adds it to the
   composition draws, closing IU0's draw-call gap for scenes. Not chosen:
   counts kept by the scene renderer alone.

Asked 2026-11-10 for PR 3; answered by the lead the same day.

5. **Where the scene renderer lives** (lead): a new crate,
   `crates/scene3d-gpu` (`vapors-scene3d-gpu`), so `vapors-scene3d`
   stays free of the GPU. Not chosen: a `gpu` feature of
   `vapors-scene3d`; the renderer in `vapors-app`.
6. **How the application reaches the scene and its geometry** (lead):
   `SceneRenderer::new(Rc<RefCell<Scene>>, Rc<RefCell<Meshes>>)`, shared
   as the racer shares its state. `Meshes::geometry(positions, indices)`
   validates (no positions, no indices, a count not a multiple of 3, an
   index out of range, a non-finite position) and holds the geometry
   until it is released (row 5). Several renderers may share one
   `Meshes` (two panels on one scene, or a renderer made again after an
   unmount): each uploads, in `render`, every piece a mesh node names
   that it has not uploaded itself. A piece issued but no longer held
   is refused at the frame, naming the node and the id. `Meshes` is in
   `vapors-scene3d`, which issues the `GeometryId`s. Not chosen: an
   upload call taking the device, which needs the application to hold
   the renderer or the device before mount.
7. **A mesh's geometry and colour** (lead): `NodeKind::Mesh { geometry:
   GeometryId, colour: Colour }`, so a mesh node cannot lack geometry,
   matching decision 1's `<Mesh geometry={..}>` prop. A `GeometryId` from
   another `Meshes` is refused at the frame, naming the node and the id.
   `Scene::add` cannot detect a foreign `GeometryId`, because the scene
   holds no `Meshes`; only the renderer, which holds both, can, and does
   so at render. That is by design. 3a-2 must return that refusal to
   the caller of `render`, not log it.
   `Colour` is sRGB-encoded channels from 0 to 1, drawn unlit, until
   materials come in slice 3. Not chosen: a binding table outside the
   node, refusing an unbound mesh at the frame.
8. **How `SurfaceFrame` reports work** (lead): a `work: &WorkCounter`
   field; the renderer issues its writes and draws through it and the
   painter adds its take to `FrameCounts::surfaces` (decision 4's
   shape).
9. **CSS reaches the scene** (Tom, 2026-11-10: option B, "one cascade into
   the scene"). 3D nodes are styled by the same cascade as HTML and SVG:
   enum-bound classes, custom properties and design tokens, `:hover` and
   other state pseudo-classes. CSS sets appearance (`color`, `opacity`,
   `visibility`); geometry, transforms and the camera stay typed props
   (decision 1). Every property a scene node reads goes through the same
   build-time analysis as boxes and SVG shapes (docs/briefs/
   NATIVE_SVG_BRIEF.md, "One analysis for every painted thing"): constant,
   or a known variable tracked at run time. This changes decision 1: the
   anchor stays `display: none` and outside the accessibility tree, but it
   is no longer inert to style; its computed style feeds its node. Not
   chosen: typed props only, where tokens and `:hover` would need code per
   app.
