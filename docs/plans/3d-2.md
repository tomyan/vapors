# 3D slice 2: persistent scene and camera

Slice 2 of the 3D lane (touche `docs/decisions/2026-11-09-3d-surface-first.md`;
the lane's brief is `docs/briefs/GPU_SURFACE_3D_BRIEF.md`, slice 2 under
"Implementation slices"). Acceptance, as reconciled with Tom on 2026-11-09:
show a mesh through Group/Mesh and both camera projections; prove parent
transforms, active-camera validation, invalid-input refusal and lifecycle
cleanup; compare ground and object projection so their transforms cannot
diverge unnoticed.

It also closes the two gaps IU0 found for the 3D slices
(`docs/design/incremental-contracts.md` section d): no check counts scene draw
calls, and nothing says how a scene node's signal change reaches the surface's
invalidation.

Slice 1 is done (`docs/gpu-surface.md`): the scene renderer is a
`SurfaceRenderer` on a `gpu-surface`. The racer keeps its own renderer; slice 2
does not port it.

Each PR is under about 400 lines and is built by a fresh agent. Each check is
proven by breaking what it guards, watching it fail and restoring it.

## The ground and object check

A ground plane (a mesh, y = 0) carries a marker at world point P, and an object
mesh stands at P. Rendered through one camera, the marker's centre and the
object's base land on the same backing pixel, and that pixel is
`Projection::project(P)` mapped to the viewport, within one pixel, for both
projections and for a camera moved after mount. The ground and the objects go
through one view-projection matrix, so the check fails if either path takes its
own (as the racer's ground shader and solid pipeline each build theirs today).

## Questions for the lead

1. **How scene nodes appear in `.wisp`.**
   (a) Lowercase elements in the document: `<scene>`, `<group>`, `<mesh>`,
   `<camera>` in the template vocabulary, kept out of style, layout, paint and
   hit testing, with typed values through a new `PropertyValue` variant.
   `{for}`, `{if}` and components work unchanged. Touches the compiler
   vocabulary, `vapors-dom` and the document.
   (b) Rust components with typed props (`<Group transform={memo}>`,
   `<Mesh geometry={handle}>`), mounted through the existing component-tag
   path. Each creates one inert, `display: none` element so `{for}` and `{if}`
   anchors and the children snippet have a parent, and registers a scene node
   keyed by that element's `NodeId`; a signal prop drives the node through an
   effect. No compiler or document change; typed props as the brief shows.
   (c) A Rust API only in slice 2, the `.wisp` vocabulary in slice 3.
   Recommended: (b).
2. **The active camera.** (a) The scene root names it (`camera={handle}`), as
   the lane's brief has it: a handle no camera holds, or held by two cameras,
   is refused. (b) Each camera has `active`; exactly one must be true.
   Recommended: (a).
3. **Matrix maths.** (a) The `glam` crate (MIT or Apache-2.0, no
   dependencies; not in `Cargo.lock` today). (b) A small `Vec3`, `Quat`,
   `Mat4` in `vapors-scene3d`, about 150 lines with tests. Recommended: (b)
   only if adding a crate is unwanted; otherwise (a).
4. **Scene draws in `FrameCounts`.** (a) `SurfaceFrame` gains a place for the
   renderer to report its `GpuWork`, and `FrameCounts::surfaces` adds it to the
   composition draws. (b) The scene renderer keeps its own counts, read by
   tests; `FrameCounts` unchanged. Recommended: (a), as IU0 asked for
   `FrameCounts`.
